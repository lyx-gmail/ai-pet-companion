# 延迟校时与离线结算

## 当前问题

运行中的旧逻辑在首次可信校时前执行Save或Changed时，放弃关机补时并清掉时间锚点。简单保留标记、之后对当前状态补扣也不正确：关机发生在本次喂食和睡眠之前，必须按事件顺序结算。

## 已实现并检查的独立核心

- `pet_timeline.h`保存校时前的基础状态与已接受动作的单调时间位置。首次可信校时先对基础状态补算未结算间隔，再依次重放喂食、抚摸、睡眠、唤醒和有效对话；不重新执行被拒绝的动作。
- 关机生理补算继续封顶24小时、关系封顶7天；回拨不加奖励；本次运行时间只结算一次；结果版本不倒退到历史基础状态的版本。
- `pet_checkpoint.h`把当前V3状态、待校时时间线、已运行时长编码成一个固定1228字节的V4封装。拒绝未知版本、矛盾标记、倒序/越界事件和非零保留区，读取失败不改变调用方状态。
- 可迁移已有V1/V2/V3状态，保留已确认照顾、计时余数、冷却和设置。原V3编码器仍保留。
- 两个检查文件共八组编译期断言已用ESP32-S3实际工具链通过；已加入标准构建脚本。证据为`evaluation/offline-time-core-check.json`。

## 有限时钟与容量边界

时间线最多128个已接受动作，普通Tick不占条目。超限时必须显式标记未知区间冻结，保留当前状态，不能丢弃已接受动作，也不能继续假装可以精确回放。

没有RTC且跨多次断电未获校时，无法知道每段未知间隔分别位于哪次互动之前或之后。运行层必须区分可证明的单调运行时间与这些不可定位的间隔：有歧义的间隔保守冻结并保留诊断标记，不能拼出假的精确时间线。此政策沿用“无可信时间冻结未知关机间隔”，而非处罚用户。

## 运行层接入

1. 已接入Save/Begin、Tick和成功照顾动作。设置修改不清掉补时记录，失败动作不入时间线。
2. `checkpoint_v4`为权威NVS条目；另存零时间锚点的旧版`snapshot`和完成交接标记`shadow_v4`。兼容写入按顺序分别提交，不声称跨键原子性。回退旧版产生新照顾记录后，再升级可依据交接标记选取较新的旧版状态。
3. 本地OTA使用UTC，仅本次启动成功执行有效范围内的校时后才信任时间；保留RTC值本身不可信。旧版时间基准不明或跨无时钟重启后互动顺序不可证明时，保留已确认状态并冻结未知间隔。
4. 仍需实机验证延迟校时、保存后继续运行、重复校时、断电恢复及NVS故障。编译期容量和迁移检查不能代替这些实机检查。
